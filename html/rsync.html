Using rsync with the LS-CAT Remote Access Client

The LS-CAT Remote Access Client allows you to start rsync processes to download data. This is an advanced feature: if you are unfamiliar with rsync, ssh, or ssh public key authentication then your best bet is to find someone in your lab who is familiar with these things to help you out.

Rsync copies only the data to your computer that needs copying. You can run the same rsync command many times without transfering the same files multiple times, only the new files or changed files are copied.

Instructions
  1. Copy the SSH Public Key from the LS-CAT Remote Access Client to your ~/.ssh/authorized_keys file. If this files does not exist then you can create one.
     
  2. Your LS-CAT public key should only be on one, albeit long, line. Sometimes the copy and paste will produce extra lines, just delete the extra "new line" characters.
     
  3. Make sure your authorized_keys file is only writable by the owner. (chmod 644 ~/.ssh/authorized_keys)
     
  4. Note that every person listed on the APS Safety Assessment Form (ESAF) has their own individual key and can only start rsync processes to computers using their key.
     
  5. The APS restricts both incoming and outgoing ports. For this reason we only support downloads using ssh port 22. If you cannot open port 22 on your side then this method will not work for you.
     
  6. LS-CAT will connect to your computer from the 164.54.252.0/23 (164.54.252.0 – 164.54.253.254) network and the suggested entry to your authorized_keys file enforces this. There are simple methods to further restrict the use of this key. See, for example, the instructions here.
     
FAQS
  • What is a public key? What is a private key?

    The public and private keys take the place of passwords for connecting two machines. LS-CAT generates this pair and sends you the public part. Only the holder of the corresponding private key can connect to your computer.
     
  • Where do I put in my password?

    A password is not used or needed. Only someone that has access to the corresponding private key can connect to your computer using the supplied public key. LS-CAT does not disseminate the private key.
     
  • How do I turn off access when I'm done?

    Simply remove the public key from your authorized_keys file.
     
  • There is already something in my authorized_keys file. Do I have to delete it?

    No, just add your LS-CAT authorized key on a new line.
     
  • It's not working. How do I fix it?

    Using rsync at LS-CAT is an advanced feature. Please have someone from your lab who is familiar with rsync, ssh, and/or public key authentication help you. Problems are usually either simple for you to solve (Extra lines in the public key? File permissions correct? Firewall allows tcp port 22 from 164.54.252.0/23) or impossible (VPN access required by your IT department). Try using the tarball download feature of the LS-CAT remote access client instead.
     
  • Can't I just ftp or ssh into your server?

    We currently only support connections initiated at LS-CAT such as the rsync sessions started using the LS-CAT Remote Access Client.
     
  • My institution does not allow incoming connections. What do I do?

    Use the "download tarball" feature of the LS-CAT Remote Access Client.
     
Debugging Checklist
Recuring theme: Ask your local expert. Rsync is an advanced feature that requires more work on your side to set up and maintain.
  1. Review your sshd and password implementations. There are a large number of bots out there that attempt brute force attacks to guess passwords via ssh. Consider using the DenyUsers and AllowUsers parameters in your sshd_config file to limit who can log in. Consider forcing the use of ssh key pairs instead of passwords.
    There are programs that monitor sshd and block machines that are running these ssh bots. You should consider using such a program. Discuss with your local expert.

  2. sshd running?
    Linux: ps -elf | grep sshd
    Mac: ps aux | grep sshd
    If this returns nothing or just your grep process then you need to start up sshd. Ask your local expert for help.

  3. sshd running on port 22 on a publicly accessable IP address?
    Linux: netstat -taun | grep 22 | grep LISTEN
    Mac: netstat -f inet -an | grep 22 | grep LISTEN
    This should show that sshd is listening on the correct IP address and port. A line that includes "0.0.0.0:22" (Linux) or "*.22" (Mac) means that sshd is listening on all the IP addresses your machine uses. Check with your local expert if you don't understand the results.

  4. Does ssh work locally?
    Keep it simple. Try to log in from the computer sshd is running on (ssh -v localhost). This should catch file permission problems. Then try another machine on the same network. Problems? Ask your local expert.

  5. Does ssh work remotely?
    Try it from home. If you cannot connect to your computer via ssh from a remote computer then we probably cannot either. There is probably a firewall rule that prevents access on port 22. You'll need your network administrators to allow access from 164.54.252.0/23 for trouble free operation. Some network adminstrators will want to narrow it down to a few machines in the 164.54.252.0/23 network. Contact us for the current list of active servers. Note this list will change without notice.

  6. Rsync installed?
    You need to have rsync installed. Type "whereis rsync" to see if it is in one of the normal places.

  7. Rsync working?

    8. Try using rsync to transfer a few files by hand. Type "man rsync" for help.
